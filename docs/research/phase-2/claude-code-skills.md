## 2. `allowed-tools` syntax (question 2)

- **Meaning [R] (verified).** It pre-approves tools for the turn that invokes the skill; it does not restrict other tools; deny and ask rules still win; the grant is cleared when the user sends the next message. Workspace trust does not gate it.
- **Forms [T] (verified, extended).** All of these work at runtime: a space-separated string (`Bash(python3 *) Bash(python *) Bash(py -3 *)`), a comma-separated string, a quoted string, a YAML list, a YAML list with trailing `# comments`, and a flow list `[Bash(python3 *), Read]`. A pattern with a space inside the parentheses survives the space split. `Bash(python3 *)` does not cover `python` and `Bash(python *)` does not cover `python3` (the other spelling was denied); listing both covers both. `claude plugin validate` rejects an `allowed-tools` that is a map or a number ("must be a string or array of strings") and accepts every other shape, including `[]` and an empty value (corrected: the first pass saw no allowed-tools error).
- **Wildcards [R] (verified).** `*` matches any text including spaces; `Bash(ls *)` also matches bare `ls` but not `lsof`; `Bash(ls*)` matches both; a trailing `:*` is an equivalent spelling of ` *`. Each part of `a && b`, `a ; b`, `a | b` is matched on its own; a few wrappers (`timeout`, `time`, `nice`, `nohup`, `stdbuf`) are stripped. Tested [T] (verified, corrected): `echo start && python3 x.py && echo end`, `python3 x.py | head -1`, `python3 x.py | tr a-z A-Z` and `cd out && python3 x.py` ran under `Bash(python3 *)`. `python3 x.py ; python3 -c "print(7)"` also ran under `Bash(python3 *)`, because both parts match the broad pattern; the second part is denied ("The following part requires approval") only under the script-prefix pattern. `python3 x.py && rm -f y` was denied for the `rm` part.
- **Variables in patterns (corrected).** `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}` are substituted inside **Bash** rules in `allowed-tools` (documented, tested for root, skill dir and project dir) [R, T] (verified). The first pass concluded they are not substituted in `Read(...)` patterns. That is wrong: they are substituted there too (the docs name only Bash rules, so this is observed, undocumented behaviour). The first pass's `Read(${CLAUDE_PLUGIN_ROOT}/**)` failed because of path anchoring: the substituted path is absolute and starts with `/`, and a single leading `/` anchors a Read/Edit rule at the project folder (permissions.md pattern table), so the rule pointed at `<cwd>/tmp/...`. With one more leading slash the rule matched: `Read(/${CLAUDE_PLUGIN_ROOT}/**)`, `Read(//${CLAUDE_PLUGIN_ROOT}/**)`, `Read(/${CLAUDE_SKILL_DIR}/**)` and `Edit(/${CLAUDE_PROJECT_DIR}/out/**)` all granted exactly the intended paths and refused `other/` [T], also when the plugin path contains a space and when the plugin is loaded in place from a local-directory marketplace. The same patterns without the extra slash granted nothing [T]. What the Windows form (`C:/Users/...`, matched after conversion to `/c/Users/...`) does with this is [U]. A shell variable such as `$PWD` in a pattern is not expanded: a pattern `Bash(python3 $PWD/x.py)` matched the command text `python3 $PWD/x.py` and not the expanded path; a pattern with the absolute path did not match a command that uses `$PWD` ("A variable in this command can't be checked before it runs") [T]. No path normalisation: `.../scripts/../templates/x.py` matched `.../scripts/*` [T] (verified).
- **Quoting trap [T] (verified, extended).** The pattern is matched against the command text. Four-way result: unquoted pattern `Bash(python3 ${CLAUDE_PLUGIN_ROOT}/scripts/*)` allowed the unquoted command and **denied** the same command with the path in double quotes; opening-quote pattern `Bash(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/*)` allowed the quoted command and **denied** the unquoted one. A closed-quote form `Bash(python3 "${CLAUDE_PLUGIN_ROOT}/scripts/probe.py" *)` allowed the quoted command with arguments, without arguments and with `-c` as an argument to the script, and denied `other.py`. With a real plugin path that contains a space (`.../plug sp/vfy/...`) the same matrix held, and the unquoted/unquoted pair was allowed but then broke: the shell split the path and Python failed. The substitution is never quoted, so SKILL.md text must quote every use. Working patterns: `Bash(python3 *)`, or the opening-quote form, which matched the quoted command also with a space in the path.
- **Breadth [T] (verified).** `Bash(python3 *)` lets `python3 -c "<anything>"` run (it ran in a skill and in the subagent it launched). The script-prefix form denied `python3 -c`. `PYTHONUTF8=1 python3 x.py` was denied under `Bash(python3 *)`, also inside a `!` injection; only some known-safe variables are stripped before matching [R, T].
- **File tools [R, T] (verified, extended).** `Read` and `Edit` rules take gitignore-style paths: `betterpaper/**` (relative to the working folder), `./betterpaper/**`, `/betterpaper/**` and `//abs/path/**` all let `Write` create files, with their missing parent folders, under the allowed folder and refused `other/note.txt`. **An `Edit(path)` rule governs Edit, Write and NotebookEdit** [R]; `Write(path)` is accepted but never consulted, and it granted nothing [R, T]. A bare `Edit` did not allow the Write tool; a bare `Write` allowed every path [T]. `Edit(out/*)` also allowed `out/sub/x.txt` (gitignore semantics: a matching directory covers its contents), so `/*` is not narrower than `/**`; `Edit(out/a/**)` did not leak to the sibling `out/b/` [T]. An `Edit(path)` allow rule also covers Bash output redirections: `python3 x.py > out/y.txt` ran with `Edit(out/**)` and needed approval without it [R, T]. `Write` creates missing parent directories, so empty directories need a placeholder file or `Bash(mkdir -p betterpaper/*)` (tested: allowed under the pattern, `mkdir -p other/x` needed approval) [T]. Python scripts that open files themselves are not covered by Read/Edit rules [R].
- **Reads outside the working folder (corrected).** Default mode refuses `Read` of the plugin directory and of the skill's own directory, and Bash `cat` there ("may only concatenate files from the allowed working directories"), also with `Bash(cat *)` allowed [T] (verified; `ls` not re-tested). A bare `Read` allowed it but is not path-limited [R, T] (verified). `Read(//abs/path/**)` works [T] (verified). `Read(~/.claude/plugins/**)` allowed a plugin placed under `$HOME/.claude/plugins/cache/...` [T] (verified, re-run with a test HOME), but it covers neither a `--plugin-dir` plugin, nor a plugin from a local-directory marketplace (the session loaded it in place from the marketplace folder), nor an install made with `CLAUDE_CONFIG_DIR` set (the plugins root is then `$CLAUDE_CONFIG_DIR/plugins`: the cache copy of a directory-marketplace plugin landed in `$CLAUDE_CONFIG_DIR/plugins/cache/<marketplace>/<plugin>/<version>/` although the session loaded the source folder, and `${CLAUDE_PLUGIN_DATA}` resolved to `$CLAUDE_CONFIG_DIR/plugins/data/<id>/`) [T]. `Read(/${CLAUDE_PLUGIN_ROOT}/**)` worked for the `--plugin-dir` plugin, the local-directory marketplace plugin (also with `CLAUDE_CONFIG_DIR` set) and the test-HOME cache [T]; it is the better rule. A Read allow rule on the plugin folder also lets `cat "<plugin file>"` work, in the Bash tool and in a `!` injection, with no `Bash(cat *)` rule [T]. For a real GitHub install the cache is `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` [R, loading.md] but I could not install that way [U].
- **Subagents [T] (corrected, extended).** A skill's `allowed-tools` also reached the subagent it launched in the same turn, for `Write` under an `Edit(out/**)` rule (other paths still denied), for `python3 -c` under `Bash(python3 *)`, for `Read(/${CLAUDE_PLUGIN_ROOT}/**)`, and for the agent of a `context: fork` skill; without the grant the same calls were denied. (First pass: `WebFetch` passed the permission check with the grant.) `Agent` needs no entry: launching a subagent does not prompt [R] (verified).
- **Expiry [T] (verified).** A write was allowed in the invoking turn and denied in the next user message (second `-p --resume` turn); invoking the skill again in a third turn re-applied the grant. With a scripted permission host (stream-json) the second message's `Write` raised a permission prompt instead of failing silently.
- **Tool names [R] (verified).** `Agent` (old name `Task` still works), `AskUserQuestion`, `WebFetch(domain:x)`, `WebSearch`, `PowerShell(...)`. On Linux/macOS/WSL the main session has no `Glob`/`Grep` tool by default (the 2.1.293 init tool list had neither) [R, T]; a subagent whose `tools` list names them gets working `Glob` and `Grep` (both ran, with no `Bash`) [T] (corrected: the first pass had only a self-report).
- **Sketch, tested as one block [I, T]:** see section 11a (revised).

## 4. Asking the user questions (question 4)

- The tool is `AskUserQuestion` (header at most 12 characters, 2-4 options, `multiSelect`, an automatic "Other" free-text row) [R: `agent-sdk/user-input.md`, `tools-reference.md`] (verified). **Question limit (corrected):** the page states "each `AskUserQuestion` call supports 1-4 questions with 2-4 options each" (Limitations section), so the plan's "batches of at most four" matches the documented limit [R]. Permission needed: none [R tools-reference]; listing it in `allowed-tools` is accepted by validate and unnecessary [T, R] (verified).
- **Never in subagents** (removed even if listed) [R sub-agents.md] (verified; a plugin agent with `tools: Read, AskUserQuestion` reported `NO-SUCH-TOOL`, also with a permission host attached [T]). Denied in `dontAsk` mode; removed under `--permission-prompts none` [R] (verified).
- **Non-interactive mode [T] (verified, extended).** In plain `claude -p` the tool is not in the tool list; the call fails or the model says it is unavailable, in default mode, in `dontAsk`, with `--tools Read,AskUserQuestion,Write`, and with `AskUserQuestion` listed in `allowed-tools`. With a permission host attached (`--input-format stream-json --output-format stream-json --permission-prompt-tool stdio`) the tool **is** in the tool list and works: the host receives a `can_use_tool` request for `AskUserQuestion` and returns the answers (tested with a script, not a human at a terminal). So an init interview needs either flags, a plain-text turn, or an interactive/SDK host; `--defaults` (G1) is the only path for plain `-p`.
- **Grant and questions (corrected, was [I, untested]).** With the scripted host, a skill with `allowed-tools: Edit(out/**)` that asked an `AskUserQuestion` question and then wrote a file inside the same turn wrote it with no permission prompt: the grant survived the question [T, scripted host]. A second user message ended the grant (previous bullet in section 2). A plain-text interview that spans messages therefore loses the pre-approval before the files are written. Real human-driven dialogs remain untested [U].

## 5. Namespacing and agents (question 5)

- **Skills [R, T] (verified).** A plugin skill `skills/init/SKILL.md` runs as `/betterpaper:init`. The bare `/init` also resolves to a plugin skill unless another command owns it, and `init` is a built-in command, so bare `/init` stays the built-in [R]; the `slash_commands` list showed both `vfy:init` and `init` [T]. Bare `/e-dmi` resolved to the plugin skill [T]. The README must say `/betterpaper:init`.
- **Agents [R, T] (verified, corrected where noted).** `agents/source-verifier.md` becomes `betterpaper:source-verifier`; subfolders add segments. A name containing `:` is reserved. The Agent tool call `subagent_type: "vfy:h-echo"` worked; **a bare `h-echo` failed** ("Agent type 'h-echo' not found. Available agents: ... vfy:h-echo ...") (corrected, was [U]). A plugin agent file without `name` was addressed by its file name (`vfy:h-noname`) [T]. A user can also write `@agent-betterpaper:source-verifier` or start `claude --agent betterpaper:<name>` [R] (verified; for `--agent` the docs say a bare plugin agent name also works [R]).
- **Plugin agent fields [R] (verified).** Supported: `name`, `description`, `model`, `effort`, `maxTurns`, `tools`, `disallowedTools`, `skills`, `memory`, `background`, `omitClaudeMd`, `isolation`, `color`, `experimental.cacheTtl`. **Ignored for plugin agents:** `permissionMode`, `hooks`, `mcpServers`, `initialPrompt`. Only `name` and `description` are required; `tools` is a comma string or a YAML list (a list with trailing comments worked [T]); `model` takes `sonnet`, `opus`, `haiku`, `fable`, a full ID or `inherit`. Validate accepted all of these and flagged none of the ignored ones [T] (verified). Runtime checks [T]: `permissionMode: bypassPermissions` was ignored (a `touch` through Bash and a Write were both denied); a `hooks:` entry that would block every Read did not fire; a bogus `model` passes validate and fails when the agent is spawned ("model_not_found", HTTP 404); a `skills:` entry preloads a normal skill (scoped or bare name) and does not preload a `disable-model-invocation` skill. An agent file with unparseable YAML still loads, under its file name, with every other field dropped [R] (validate message, verified), which for a reviewer means no `tools` restriction [I]; validate flags it as an error [T] (verified).
- **Launching from a skill [T].** The skill body says "use the Agent tool with `subagent_type` `betterpaper:<agent>`". Two Agent calls in one assistant message both started (verified). Background or foreground depends on the `run_in_background` argument the model passes (corrected): with `true` the result was "Async agent launched" and the text came back as a later `task_notification` before the final answer (verified); with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` every Agent call returned its result synchronously, and with the variable at 0 the model passed `run_in_background: false` on its own and the result was synchronous too, which settles that foreground runs work. Wave 2 must therefore wait for the wave-1 notifications whenever wave 1 is started in the background. ## 6. Shell on Windows, Python spellings, paths (question 6)

- **Which shell [R] (verified).** Native Windows with Git for Windows: the Bash tool runs Git Bash; the PowerShell tool is also available (on by default for claude.ai and Console accounts). Without Git for Windows: PowerShell is the shell tool. WSL: Bash. The plan must expect both shells. **Added from the docs:** when the PowerShell tool is enabled, Claude treats PowerShell as the primary shell and keeps Bash for POSIX scripts, so on such a machine Claude may well pick PowerShell, where `Bash(...)` pre-approvals do not apply [R tools-reference]; a Bash deny rule, even a scoped one, turns the PowerShell tool off on Windows with Git Bash [R]; for `!` injection the default `shell: bash` falls back to PowerShell when bash is missing, but an explicit `shell: bash` then fails the invocation ("requires bash ... but Git Bash was not found") [R skills.md].
- **Rules are per tool [R] (verified).** `Bash(...)` rules do not apply to PowerShell commands; PowerShell has `PowerShell(...)` rules with the same wildcard shape, case-insensitive, with cmdlet alias canonicalisation. A skill that lists only `Bash(python3 *)` is unattended-safe on Linux/macOS but not for a PowerShell user [R, I]. I could not run PowerShell here (`pwsh` is not installed) [U].
- **Python names [R] (verified).** Source: `https://raw.githubusercontent.com/python/cpython/main/Doc/using/windows.rst` (the official docs' source; branch 3.9 for the older launcher text). The current text recommends `py` where several versions exist (and `python` otherwise); `python3` is a catch-all "not meant to be widely used"; typing `python` can open the Microsoft Store app or give "command not found" when aliases are off; `py` is "not recognized" if the launcher is missing. The 3.9 text shows `py` (latest Python), `py -3.7` and `py -2`; a bare `py -3` is not spelled out in either text, but PEP 397 (the launcher's specification) describes `py.exe -3` as launching the latest Python 3.x [R]. Whether `py -3` still behaves so with the newer Python install manager is [U]. A safe probe order is `py -3` (or `py`), `python`, then `python3` on Windows; `python3` then `python` on Linux and macOS [I]. A probe should run `-c "import sys; print(sys.version_info >= (3, 9))"`, since `python` may be Python 2 on old systems [I]; as a `!` injection that needs an allow rule (section 3).
- **Encoding [R] (verified).** Before v2.1.214, Python printing non-ASCII from the PowerShell tool could crash with `UnicodeEncodeError`; scripts should still reconfigure stdout to UTF-8 themselves (plan D19) because an env prefix such as `PYTHONUTF8=1` is not auto-allowed [T] (verified).
- **Spaces [T, I] (verified on Linux).** Always quote script paths and workspace paths in the command; the slug rule `[a-z0-9-]+` keeps the workspace part safe.

## 7. Executable bit (question 7)

Scripts run as `python3 "<path>"` need no executable bit: the probe scripts were mode 644 and ran in every run [T] (verified). A local-marketplace install copied a 644 file as 644 into the cache [T] (the first pass also saw 755 stay 755; not re-tested). Note that for a relative-path plugin in a local-directory marketplace the session loaded the plugin in place from the marketplace folder, not from the cache copy (`${CLAUDE_PLUGIN_ROOT}` was the source folder) [T], which matches loading.md [R]. The bit matters only for a `bin/` executable (put on PATH, `chmod +x` per docs) and shell-form hooks [R]; `bin/` plugins are not installed by claude.ai or Cowork [R]. Windows checkouts have no mode bits [I]. Recommendation: invoke scripts as `<python> "<path>"` and do not use `bin/`.

## 9. What `claude plugin validate` checks (question 9)

Run on a plugin directory it checks the manifest and also the skill and agent files [R, T] (verified); a clean file prints nothing about itself, a flagged file is named, and `--json` lists only flagged files in `contents` [T] (verified). Results of 94 variants in the first pass and 91 more in the verification pass [T] (verified, corrected where noted):

| Outcome | Variants |
|---|---|
